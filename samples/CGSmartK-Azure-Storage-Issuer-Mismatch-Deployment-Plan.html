CGSmartK Azure Storage Authentication Incident

Diagnosis, deployment scope, and remediation plan

Prepared: 4 August 2026

Executive summary

  • Failing service: Azure Blob Storage, while listing metadata blobs in the knowledge-documents container.
  • Immediate cause: Storage rejected the bearer token because its issuer did not match the Microsoft Entra tenant expected by the Storage account.
  • Deployment scope: Publish and deploy only src/CGSmartK.Web/CGSmartK.Web.csproj to web-smartapp-f59ee617.
  • Worker scope: There is no independently deployed ingestion microservice. The ingestion worker runs inside the Web application.

1. Which service is failing?

The failing dependency is Azure Blob Storage. The request fails while BlobDocumentRepository.FindByHashAsync enumerates metadata blobs before a new PDF is saved.

  1. KnowledgeController.Upload receives the PDF.
  2. KnowledgeService.UploadAsync validates it and checks for duplicates.
  3. BlobDocumentRepository.FindByHashAsync calls BlobContainerClient.GetBlobsAsync.
  4. Azure Blob Storage returns HTTP 401 InvalidAuthenticationInfo with “Issuer validation failed. Issuer did not match.”

The request has not yet reached Document Intelligence, Azure OpenAI embeddings, Azure AI Search, or Azure OpenAI chat. The supplied stack trace therefore does not show those services failing.

2. What the issuer mismatch means

The Storage challenge identifies tenant 8ac76c91-e7f1-41ff-a89c-3553b2da2c17 as the expected authorization tenant. The repository deployment documentation identifies b24388d9-c6ca-4c64-a601-5edb6e666e1e as the intended application subscription tenant. This strongly indicates that the token issuer and the tenant expected by the targeted Storage account are not aligned.

This is not the same as ordinary missing RBAC. An issuer mismatch is an authentication failure. A correctly issued token without Blob data permissions normally produces an authorization failure such as HTTP 403 AuthorizationPermissionMismatch. Assigning another role cannot repair a token issued by the wrong tenant.

Likely causes

  1. SmartAssist__Storage__AccountName points to a different Storage account than intended.
  2. The App Service and Storage account are associated with different tenants or subscriptions.
  3. The Web App system-assigned managed identity is not the expected identity.
  4. AZURE_* App Service settings select an unintended service principal or user-assigned identity.
  5. A deployment slot has settings that differ from production.
  6. During local execution, DefaultAzureCredential selected an Azure CLI or developer credential signed into the wrong tenant.

3. What must be deployed to App Service?

Deploy only the Web project:

src/CGSmartK.Web/CGSmartK.Web.csproj

Publishing that project includes the Web, Infrastructure, Application, and Domain assemblies and their runtime dependencies. Do not deploy Domain, Application, Infrastructure, tests, scripts, or documentation as separate App Services.

The bounded ingestion queue and IngestionWorker execute in the Web App process. A separate worker App Service is not part of the current architecture.

4. Remediation and deployment plan

Phase 1 — Verify the Storage target

  1. Inspect SmartAssist__Storage__AccountName and SmartAssist__Storage__ContainerName on web-smartapp-f59ee617 and its active deployment slot.
  2. Confirm the expected values are stsmartappf59ee617 and knowledge-documents.
  3. Confirm the configured account's Blob endpoint belongs to the intended resource in resource group SmartApp.
  4. Do not add an account key or Storage connection string.

Phase 2 — Compare tenants and managed identities

  1. Confirm subscription bae405f7-48fe-48ae-a393-b10c8205792d reports tenant b24388d9-c6ca-4c64-a601-5edb6e666e1e.
  2. Inspect the Web App system-assigned identity. Confirm principal ID 41f3cdfc-208c-4f4a-8660-34eb21aa9390 and record its tenant ID.
  3. Compare that tenant with the Storage challenge tenant 8ac76c91-e7f1-41ff-a89c-3553b2da2c17.
  4. If they differ, ask the Azure owner to align the Web App, identity, and Storage resource. Do not bypass tenant validation in application code.

Phase 3 — Check credential overrides

  1. List App Service setting names beginning with AZURE_, without printing secret values.
  2. Review AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, and AZURE_CLIENT_CERTIFICATE_PATH if present.
  3. Confirm any selected user-assigned identity is intentional and belongs to the correct tenant.
  4. Repeat the check for deployment slots.

Phase 4 — Verify Blob data-plane RBAC

  1. After tenant alignment, verify that the exact Web App identity has Storage Blob Data Contributor on the Storage account, container, or an inherited scope.
  2. Do not substitute Contributor or Storage Account Contributor; those management-plane roles do not grant Blob data access.
  3. Allow time for propagation, restart the Web App, and run scripts/Test-AzureAccess.ps1. Azure CLI data-plane checks test the CLI user, not the Web App identity.

Phase 5 — Validate and deploy the application

dotnet restore CGSmartK.sln
dotnet build CGSmartK.sln --configuration Release --no-restore
dotnet test CGSmartK.sln --configuration Release --no-build --no-restore
dotnet publish src/CGSmartK.Web/CGSmartK.Web.csproj \
  --configuration Release --no-build --output artifacts/publish

Deploy the published ZIP to web-smartapp-f59ee617. The repository-supported shortcut is:

./scripts/Deploy-WebApp.ps1 -ConfirmDeployment

Phase 6 — Restart and validate

  1. Restart web-smartapp-f59ee617.
  2. Verify /health/live.
  3. Verify Microsoft sign-in and application-role authorization.
  4. Open /Knowledge as a KnowledgeAdministrator.
  5. Upload only the supplied synthetic PDF and confirm Blob persistence succeeds.
  6. Wait for status Indexed, ask a grounded question, and validate its citations.
  7. If upload succeeds but ingestion fails, investigate Document Intelligence, Azure OpenAI embeddings, and Azure AI Search in that order.

5. Operational decision tree

  • Storage setting is wrong: correct the non-secret App Service setting and restart.
  • Web App identity tenant differs: escalate to the Azure owner to align resource and identity configuration.
  • Credential override selects the wrong identity: remove or correct it through approved App Service configuration.
  • Issuer matches but Storage returns 403: correct Storage Blob Data Contributor assignment for the exact managed identity.
  • Blob upload works but processing fails: examine the hosted ingestion worker and downstream dependencies in execution order.

6. Guardrails

  • Continue using DefaultAzureCredential.
  • Do not add keys, tokens, secrets, Storage connection strings, raw prompts, document text, or generated answers to source control or logs.
  • Do not create or delete Azure resources from this repository.
  • Do not deploy when restore, Release build, or tests fail.
  • Do not enable anonymous production access to bypass authentication or authorization errors.

Conclusion: Resolve the Azure Blob Storage tenant/issuer mismatch before treating the incident as RBAC or redeploying code. Once configuration is corrected, deploy only the CGSmartK Web project; its referenced libraries and hosted ingestion worker are included automatically.
